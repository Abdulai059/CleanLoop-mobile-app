> **Purpose:** Define the logical and physical data architecture for the CleanLoop platform. This section establishes the database design principles, entity relationships, naming conventions, indexing strategy, integrity rules, audit mechanisms, and migration strategy. It serves as the authoritative reference for all persistence-related engineering decisions.
> 

---

# 20.1 Objectives

The database architecture must:

- Maintain data integrity across all modules.
- Ensure transactional consistency for critical operations such as wallets and reward redemptions.
- Support efficient querying at national scale.
- Minimize data duplication through normalization.
- Provide comprehensive auditing and traceability.
- Enable future expansion beyond Ghana without major schema redesign.
- Preserve compatibility with PostgreSQL standards.

The database is the **single source of truth** for all persistent business data.

---

# 20.2 Scope (MVP)

The MVP database is intentionally scoped to **Ghana**.

### Geographic Scope

The platform supports:

- Ghana
- 16 Regions
- Metropolitan, Municipal, and District Assemblies (MMDAs)
- Communities
- Schools
- Recovery Hubs
- Recycler Companies operating within Ghana

Future internationalization will introduce a Country entity without requiring major redesign.

---

# 20.3 Database Engine

## PostgreSQL

PostgreSQL has been selected because it provides:

- ACID-compliant transactions.
- Mature indexing capabilities.
- Foreign key enforcement.
- Advanced query optimization.
- Native JSON support.
- Strong GIS compatibility (PostGIS).
- Excellent scalability.

No database-specific features should be used unless they are part of standard PostgreSQL or intentionally documented.

# 20.4 Database Design Principles

## Principle 1 — Single Source of Truth

Each business concept has one authoritative table.

Examples:

| Entity | Authoritative Table |
| --- | --- |
| User | users |
| Household | households |
| School | schools |
| Recovery | recoveries |
| Wallet | wallets |
| Reward | rewards |

No duplicate ownership is permitted.

---

## Principle 2 — Normalization

The schema should generally target Third Normal Form (3NF):

- Minimize duplicated data.
- Separate reference data.
- Reduce update anomalies.

Controlled denormalization is acceptable only where measurable performance benefits outweigh the maintenance cost.

---

## Principle 3 — Immutable Financial Records

Wallet transactions must never be updated or deleted.

Corrections are made through compensating transactions to preserve a complete audit trail.

---

## Principle 4 — Soft Deletes

Business records should not be physically deleted during normal operations.

Instead, entities include lifecycle fields such as:

- `deleted_at`
- `deleted_by`
- `deletion_reason` (where applicable)

This supports auditing, recovery, and regulatory reporting.

Reference tables may still allow hard deletion during development or administrative maintenance.

---

## Principle 5 — Auditability

Critical entities should include:

- `created_at`
- `created_by`
- `updated_at`
- `updated_by`

Sensitive operations should also produce entries in a centralized audit log.

# 20.5 Naming Conventions

### Tables

- Lowercase.
- Snake_case.
- Plural nouns.

Examples:

- users
- households
- recovery_hubs
- wallet_transactions

---

### Columns

Use descriptive snake_case names.

Examples:

- first_name
- phone_number
- total_points
- recovery_status

Avoid abbreviations unless they are industry standard.

---

### Primary Keys

Every table uses a single primary key:

```
id UUID PRIMARY KEY
```

UUIDs reduce predictability and simplify synchronization across distributed clients.

---

### Foreign Keys

Naming convention:

```
user_id

school_id

reward_id

community_id
```

Foreign keys should always reference the primary key of the related table.

# 20.8 Geographic Data Model

Because the MVP is limited to Ghana, geography is modeled explicitly.

Hierarchy:

```
Country
    ↓
Region
    ↓
District (MMDA)
    ↓
Community
    ↓
Recovery Hub
```

Households, schools, and recyclers are linked to communities to enable localized reporting and operations.

This hierarchy also supports future regional analytics and expansion.

# 20.9 Data Integrity Rules

The database shall enforce:

- Foreign key constraints.
- Unique phone numbers.
- Unique national identifiers where applicable.
- Non-negative wallet balances (unless business rules explicitly allow temporary negative states).
- Valid status transitions enforced by application logic and, where appropriate, database constraints.

---

# 20.10 Indexing Strategy

Indexes should be created for:

- Foreign keys.
- Phone numbers.
- Email addresses.
- Wallet IDs.
- Recovery status.
- Campaign status.
- Community ID.
- Region ID.
- Creation timestamps.

Composite indexes should be added only after measuring query performance.

---

# 20.11 Transactions

The following operations must execute within database transactions:

- Recovery verification and point allocation.
- Reward redemption.
- Inventory transfer.
- Recycler purchase confirmation.
- Wallet adjustments.

This guarantees atomicity and consistency.

---

# 20.12 Migration Strategy

Database changes must be version-controlled.

Each migration should:

- Be idempotent where possible.
- Include rollback guidance when practical.
- Avoid destructive operations without explicit approval.
- Preserve production data during schema evolution.

Schema changes should be applied through a migration framework rather than manual SQL execution.

---

# 20.13 Data Retention

Operational data should be retained according to business and regulatory requirements.

Examples:

- Wallet transactions: retained indefinitely.
- Audit logs: retained indefinitely.
- Recovery records: retained for long-term reporting.
- Notifications: archived after the defined retention period.
- Temporary synchronization data: periodically purged.

Retention policies should be configurable where feasible.

---

# 20.14 Future Internationalization

Although the MVP targets Ghana, the schema should anticipate future expansion by:

- Designing region and community relationships that can accommodate additional countries.
- Avoiding hardcoded assumptions beyond the MVP where practical.
- Supporting localization and multiple currencies in future iterations without requiring a full redesign.

---

# 20.15 Acceptance Criteria

The database architecture is considered complete when:

- Every business domain has a defined ownership model.
- Naming conventions are applied consistently.
- Data integrity rules are documented.
- Transaction boundaries are identified.
- Indexing strategy is established.
- Audit and retention requirements are defined.
- The schema supports the Ghana MVP while allowing future expansion.
